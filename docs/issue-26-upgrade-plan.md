# Issue 26: Nextcloud upgrade plan

Proposed 2026-09-23 for [issue #26](https://github.com/isaac7y8y9y/nextcloud-pi-server/issues/26). This plans items 4 and 5. It authorizes no live change. Refresh time-sensitive evidence before each approved stage.

## Baseline and target

The September 23 read-only inventory found Debian 13 ARM64/v8, kernel 6.12.62+rpt-rpi-2712, Docker Engine 29.2.1, Compose 5.0.2, containerd.io 2.2.1, Nextcloud 30.0.17/PHP 8.3.28, MariaDB server 11.8.6, and Caddy 2.10.2. Nextcloud is out of maintenance mode with no database upgrade pending. The protected active-image record is in source mode and the running tags/IDs match the tracked lock. The DB has READ-COMMITTED isolation, ROW binary logging, and 169 Dynamic-format InnoDB tables. The storage mount is ext4 with about 209 GB available. Container IDs were inspected but omitted because they are ephemeral; bind them in each protected stage record. September 17 backups are stale for live use.

## Critical database decision

[Nextcloud 30](https://docs.nextcloud.com/server/30/admin_manual/installation/system_requirements.html), [31](https://docs.nextcloud.com/server/31/admin_manual/installation/system_requirements.html), and [32](https://docs.nextcloud.com/server/32/admin_manual/installation/system_requirements.html) list MariaDB only through 11.4. The Pi's 11.8.6 is already outside that range. The [31.0.14 setup check](https://github.com/nextcloud/server/blob/v31.0.14/apps/settings/lib/SetupChecks/SupportedDatabase.php) warns above 11.4. The [32.0.15 setup check](https://github.com/nextcloud/server/blob/v32.0.15/apps/settings/lib/SetupChecks/SupportedDatabase.php) accepts 11.8, but its written requirements do not; use the written range as the gate. [Nextcloud 33](https://docs.nextcloud.com/server/33/admin_manual/installation/system_requirements.html) explicitly includes 11.8. A fully in-range 30→33 path therefore needs an 11.4 database until 33 is healthy.

Proposed route: rehearse a logical export of the application database into a **separate, clean MariaDB 11.4.13** data directory. Import only application schema/data, create credentials and grants using 11.4 system tables, and verify schema counts, table integrity, collations, Nextcloud 30 status and file operations, and a 30→31 rehearsal. Never mount the existing 11.8 data directory with 11.4. Preserve its original state and the full verified backup. [MariaDB does not officially support major downgrades](https://mariadb.com/docs/server/server-management/install-and-upgrade-mariadb/downgrading-between-major-versions-of-mariadb), though it documents a clean-target logical restore as a fallback. This is a risky cross-version migration, not a routine package downgrade. The isolated rehearsal is a hard gate: if it fails, stop before any live cutover and revise the plan. Do not silently accept an out-of-range 31 stage.

Once 33.0.9 and all required background migrations are healthy, use MariaDB's [forward major-upgrade procedure](https://mariadb.com/docs/server/server-management/install-and-upgrade-mariadb/upgrading/platform-specific-upgrade-guides/upgrading-on-linux/upgrading-between-major-mariadb-versions) to reach 11.8.9. Check on-disk compatibility, `mariadb-upgrade`, tables, and Nextcloud health before 33→34. A return to 11.4 after that point requires full runtime restoration to a matching earlier state, never an older binary against newer files.

## Major and app matrix

The candidate path is **30.0.17 → 31.0.14 → 32.0.15 → 33.0.9 → 34.0.4**. Use the [official Docker image's one-major startup migration](https://github.com/nextcloud/docker/blob/master/README.md#update-to-a-newer-version), not the web updater. Confirm `occ upgrade`/repair status, apps, maintenance state, required jobs, browser and file checks at each destination.

They are compatibility candidates, not mandatory updates. Refresh `occ app:list`, app manifests, release availability, and PHP constraints before each hop. Disable third-party apps for the core migration as [Nextcloud directs](https://docs.nextcloud.com/server/stable/admin_manual/maintenance/upgrade.html), then install/re-enable compatible versions without force-enabling incompatible apps. ## Item 4: implement, rehearse, and review

1. Start a fresh implementation branch/worktree from current `origin/main`, using this plan as reference. Extend the existing `scripts/lib/image-lock.sh`, `scripts/lib/active-images.sh`, `scripts/lib/atomic-transaction.sh`, `scripts/deploy-config.sh`, and root-owned privileged dispatcher where needed. A dedicated image-update interface must bind exact tag, registry index/ARM64/config digests, expected loaded ID, target, live pre-state, backup/recovery evidence, clock, actions, exclusions, and single-use expiry. Its plan must be read-only and redacted; only its approved apply may retrieve the exact bound images and must prove the loaded ID before activation. Do not add pulls to the normal launcher or use `latest`, broad Compose pull, or image pruning.
2. Stage Compose and lock changes through `compose/docker-compose.yml`, `config/image-lock.env`, and `scripts/render-deployment-config.sh` one target at a time. The existing config deployer requires images to be already installed and source-locked; it cannot by itself perform this upgrade. Its rollback only restores Compose/Caddy and the active record. First start of a new Nextcloud or MariaDB container is the conservative **runtime-may-have-changed boundary**, because the official Nextcloud entrypoint can migrate the persistent tree and database during startup. Only failures before that start can use image/config-only rollback. After it, stop the stack and restore a matching full runtime, Compose/Caddy state, prior images, and protected active record together, or repair forward under a new approved plan. The protected active record, source lock, running IDs, and verified image archive must agree at stage completion.
3. Design and implement an approved **live full-runtime restore** path because [`scripts/test-runtime-recovery.sh`](recovery.md#runtime-recovery-drill) only restores into disposable paths. Bind a verified runtime backup, matching old images and Compose/Caddy, protected active-record pre-state, exact target/mount, stopped services, and private staging. Restore database, Nextcloud tree, and Caddy volumes from the same quiesced point, then restore configuration/active-image state and verify health before reopening service. Preserve failed state for diagnosis. Never attempt an in-place MariaDB or Nextcloud downgrade or a partial config-only rollback after first target start.
4. Build a protected, isolated rehearsal for the clean 11.8→11.4 logical migration and the later 11.4→11.8 forward upgrade. Reuse verified private backup material, keep data and credentials off Git and out of command output, and test import, schema counts, `mariadb-check`, `occ status`, 30→31 behavior, file operations, and failure cleanup. Extend the backup workflow with an approved final quiesced snapshot that keeps external writes and background jobs blocked from capture through stage acceptance; the existing `backup-runtime-state.sh --apply` reopens service after capture and is insufficient alone. The rehearsal and any required disposable Pi state have their own explicit approval. If a realistic rehearsal is unsafe or fails, stop the rollout and revise this plan.
5. Add targeted failure-injection/integration tests for wrong digest/platform, tag drift, source-lock/active-record mismatch, absent storage mount, stale backup, interrupted pull/import, expired/replayed approval, schema-boundary failure, rollback/restore, and retained recovery material. Update sanitized docs/fixtures. Run `scripts/run-tests.sh pr`, documentation and publication-safety checks, Linux privileged CI, and the required `code_review` and `review_my_pr` reviews. No private image archives, active records, credentials, or live runtime data enter Git.

The final snapshot workflow needs a protected **ingress freeze** owned by the root-only privileged dispatcher. Before capture, pause the background-job timer, put Nextcloud in maintenance mode, and block **all** non-loopback traffic to Caddy's published TCP 80/443 ports at the actual Docker forwarding/firewall boundary, including already-established IPv4/IPv6 connections and keep-alive sessions. Close or drain existing external flows and wait for in-flight application writes and DB transactions to finish; refuse capture if quiescence cannot be proved. Preserve SSH and unrelated NAS ports. From a separate LAN client, prove both new and pre-existing connections cannot send an application write over either available IP family; on the Pi, prove loopback HTTPS still works. Only then take and verify the final snapshot. The freeze remains installed while Nextcloud maintenance mode is off for migration checks: `scripts/health-check.sh` probes HTTPS from the Pi via `127.0.0.1`, and `scripts/preflight.sh --conformance` checks Compose/ports over SSH, so they can run without reopening LAN writes. Test the chosen nftables/iptables/Docker path on the deployed network backend; do not assume a rule is effective merely because it installed. Bind rule identity and prior firewall state to the transaction. On failure or interruption, leave the ingress freeze in place until verified full recovery or forward repair and a separately approved release. On successful pre-open acceptance, release it exactly once, restore the timer state, then test LAN browser upload/download. Tests must prove activation, old/new-flow denial, in-flight drain, loopback health, IPv4/IPv6 coverage, interruption retention, and exact release without leaving a permanent firewall change.

Merge generic machinery before the first live version change. Do **not** merge a final `config/image-lock.env` ahead of production: its normal startup would reject the still-running old baseline. For each item-5 stage, create a reviewed candidate with that stage's Compose and metadata-derived expected image IDs; approve and fetch exact digests, verify actual loaded IDs, apply and prove the stage, then merge that stage's baseline. Keep the stage worktree and recovery evidence until resolved.

## Item 5: bounded rollout and acceptance

1. Refresh the read-only Pi inventory, installed apps, mount UUID/space, scheduler, live images/IDs, DB state, clock, and package candidates. Recreate and verify fresh configuration, runtime, and prior-image recovery material within repository freshness limits. Run the existing isolated image and runtime restore-readiness checks. Immediately before each stage, install and prove the protected ingress freeze, pause background jobs, capture and verify a **final quiesced runtime recovery point**, and keep the freeze in place until migration and loopback/SSH pre-open health are accepted. The old backup helper's normal reopening behavior cannot serve this role by itself. Each mutation has its own exact approval and stop point.
2. Only after a successful isolated rehearsal, cut over a clean MariaDB 11.4.13 database while Nextcloud remains at 30.0.17. Preserve the original 11.8 state. Verify DB, `occ`, HTTPS and read-only application access while writes remain blocked. On failure, recover the complete pre-cutover runtime before accepting new writes.
3. Upgrade 30→31, 31→32, and 32→33, each as a separate approved stage with its own final quiesced recovery point and MariaDB 11.4.13. Install compatible apps at each endpoint and complete required DB/app migrations and background jobs. Check maintenance off when appropriate, `scripts/health-check.sh`, `scripts/preflight.sh --conformance`, and no direct app host port before reopening. Stop on failure; recurring jobs need not make the total queue zero.
4. With 33 healthy, perform the separately approved forward MariaDB upgrade to 11.8.9. Verify `mariadb-upgrade`, table integrity, Nextcloud, and a fresh post-upgrade recovery point. Then do 33→34 with the same independent gates and approval. After each accepted reopening, test browser upload/download on macOS and Windows. If that post-open check fails, block new writes and investigate any accepted writes before considering restoration; never blindly restore the pre-open snapshot over later user data.
5. Upgrade Caddy to 2.11.4 separately, validate the existing Caddyfile against the selected image, and confirm internal HTTPS/certificate behavior. Upgrade Docker Engine/CLI with a compatible containerd.io package in a separate administrator maintenance window. Retain Compose 5.0.2 unless actual testing finds incompatibility. Verify no-pull launcher, storage gate, image identity, isolated recovery helpers, scheduler, shutdown/reboot ordering, and health after the daemon update.
6. Verify final versions, no pending required DB/background migrations, source-lock/active-record identity, DB/Caddy/HTTPS, storage mount, macOS and Windows LAN access, and fresh config/runtime/image recovery artifacts. Update current-configuration, deployment, startup, recovery, operations, known-risks, tests, and `CHANGELOG.md` with the **proven** baseline. Require repository CI and publication-safety checks.

Every stage stops if an image/app candidate changes, a backup or restore gate fails, the mount differs, or health fails. Once a schema migration has run, changing an image tag is not a rollback. Full restoration to a matching earlier runtime state needs its own approval. The September 17 one-off PHP preview memory failure should be monitored; a recurrence before the next hop requires diagnosis.
